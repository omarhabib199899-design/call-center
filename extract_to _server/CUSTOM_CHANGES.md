# Custom feature: assign agents to WhatsApp numbers

Added 2026-10-17.

Stock WhatsCRM only lets an agent be assigned to **individual chats**. This
change adds assignment at the **number (instance)** level: an agent assigned to
a number sees every chat that arrives on it, automatically, and a number can be
shared by several agents.

Chat-level assignment is untouched and keeps working exactly as before. The two
mechanisms are OR'd together.

---

## ⚠️ Read this before applying a vendor update

A vendor update overwrites `server.js`, `app.js` and `helper/socket/index.js`.
The new files are safe, but **the three edits below will be lost** and the
feature will silently stop working (agents fall back to chat-level only).

After any update, re-apply the three edits in *Modified files*. Pristine copies
of the originals are in `../_vendor_originals/` for diffing.

### 3. `helper/socket/index.js` — two edits

**a) Import, at the top of the file after the `query` require:**

```js
// [CUSTOM] agent <-> WhatsApp number assignment
const { buildAgentChatCondition } = require("../agentInstances");
```

**b) Inside the `get_chat_list` case**, replace the `if (isAgent) {` block's
chat filter. Stock code:

```js
            // Then filter chats assigned to this agent.
            conditions.push(`(
              assigned_agent LIKE ? OR

            )`);
```

## How it works

`beta_chats.origin_instance_id` already records which number each chat arrived
on, as JSON written by the QR layer:

```json
{"id":"201094646331:63@s.whatsapp.net","lid":"186775309943014:63@lid"}
```

`agent_instances` maps an agent to one or more `instance.number` values. The
chat-list filter becomes:

```sql
(   assigned_agent     LIKE '%"id":5%'              -- stock, per chat
 OR assigned_agent     LIKE '%"id":"5"%'            -- stock, per chat
 OR origin_instance_id LIKE '%"id":"201094646331%'  -- new, per number
)
```

## Safety properties

- **Migration not run?** `getAgentNumbers` swallows `ER_NO_SUCH_TABLE` and
  returns `[]`, so the inbox falls back to stock behaviour instead of breaking.
- **Tenant isolation.** `/set` only accepts numbers belonging to the calling
  owner and agents whose `owner_uid` matches, so one tenant can never grant its
  agents access to another tenant's traffic.
- **No agents affected until assigned.** An agent with no rows in
  `agent_instances` behaves exactly as before.

## Known limitation

`load_conversation` in `helper/socket/index.js` does **not** verify assignment —
it scopes only by `owner_uid`. An agent who knows another chat's `chat_id` can
load its messages. This is pre-existing stock behaviour, not introduced here,
but it means the chat list is a filter rather than a hard security boundary.

## Tests

`test-agent-numbers.js` (kept with the deployment notes) covers: stock behaviour
before assignment, visibility after assignment, isolation between agents, number
sharing between two agents, chat-level assignment still working, and
notification targets. All 8 assertions passed on 2026-10-17.

# Custom feature: Click-to-WhatsApp ad attribution

Added 2026-10-18.

Records which ad a customer arrived from. WhatsApp attaches the ad's details
to the first message sent after someone taps a Click-to-WhatsApp ad. Stock
WhatsCRM ignores this for QR sessions and only `logger.log()`s it for Meta
Cloud API, so the information was being thrown away.

Report page: `/ad-sources.html`

## New files

| File | Purpose |
|---|---|
| `database/chat_ad_source.sql` | Creates the `chat_ad_source` table. Idempotent. |
| `helper/adSource.js` | Extracts + normalises the referral from both transports, and stores it. |
| `routes/adSources.js` | Owner-only API at `/api/ad_sources/*`. |
| `client/public/ad-sources.html` | Bilingual report with per-ad totals and CSV export. |

## Modified files

### `server.js` and `app.js`
After the `agent_numbers` line:
```js
// [CUSTOM] click-to-WhatsApp ad attribution
app.use("/api/ad_sources", require("./routes/adSources"));
```

### `helper/addon/qr/processThings.js`
Import at the top:
```js
const { captureFromBaileys } = require("../../adSource");
```
And after `saveMessageToConversation(...)` in the Baileys path:
```js
captureFromBaileys({ body, uid, chatId }).catch(() => {});
```

### `helper/inbox/meta/index.js`
Import at the top:
```js
const adSource = require("../../adSource");
```
And after `saveMessageToConversation(...)` in `processMetaMsg`, a `record()`
call guarded by `if (message?.referral)`.

### `client/public/agent-numbers-link.js`
Now renders two floating buttons instead of one.

## Where the data comes from

| Transport | Path |
|---|---|
| QR / Baileys | `message.<anyType>.contextInfo.externalAdReply` |
| Meta Cloud | `message.referral` |

An ad is distinguished from an ordinary link preview — which reuses the same
envelope — by the presence of `sourceId`, `ctwaClid` or `showAdAttribution`.

## Limits

Only customers who *tapped an ad* can be attributed. Someone who saved the
number, replied to a normal post, or typed the number in carries no referral
data, and no amount of code can recover it.

## Safety

Capture is fire-and-forget (`.catch(() => {})`) and a missing table is
swallowed, so attribution can never delay or break message delivery.

## Tests

`ad-test.js`: 21 assertions covering extraction from text and image messages,
Meta Cloud payloads, rejection of ordinary link previews, malformed input,
storage, de-duplication and Arabic round-tripping. All passed 2026-10-18.

# Other custom changes (added 2026-10-18)

A vendor update overwrites every vendor file listed here. Re-apply after updating.
Pristine copies of the originals are in `../_vendor_originals/`.

## `routes/messenger.js` — Messenger login (two edits)

1. **`/auth-url`**: when `MESSENGER_CONFIG_ID` is set in `.env`, the dialog is
   opened with `config_id` on the versioned path `/v24.0/dialog/oauth`. Apps
   created with a "Business messaging" use case get Facebook Login for Business,
   which refuses the classic `scope=` dialog. With the variable unset the original
   classic flow is used unchanged.
2. **`/callback`**: `/me/accounts` is now read with `limit=100` and its paging
   cursors followed to the end. Stock code read only the first batch, so accounts
   with many pages silently lost the rest. Also logs how many pages came back.

`.env` needs: `MESSENGER_CONFIG_ID=<Login Configuration ID from Meta>`

## `middlewares/agent.js` — agent sessions
Compares `tokenVersion` numerically with NULL treated as 0, treats only an
explicit `is_active = 0` as deactivated, and no longer sends `logout: true` for
missing/invalid/unauthorized tokens. Real security cases (password change,
deactivated agent) still log out.

## `.env`
`FRONTENDURI` and `BACKURI` must each be ONE URL with no commas. The code builds
media and callback links straight from them; a comma-separated list breaks every
image, audio and OAuth link.

## `client/public/index.html` — script tags
Loads `/agent-numbers-link.js`, `/session-guard.js` and `/ad-badge.js`.

| File | Purpose |
|---|---|
| `session-guard.js` | Keeps Back inside the agent panel; Back closes an open chat, then asks before leaving. |
| `ad-badge.js` | Shows the "came from ad" banner over an open conversation. |
| `agent-numbers-link.js` | Floating shortcuts to the agent-numbers and ad-sources pages. |

## `routes/adSources.js`
Adds `GET /api/ad_sources/lookup` (owner or agent token) used by `ad-badge.js`.

# Instagram through a connected Facebook Page

Added 2026-10-19.

Stock WhatsCRM links Instagram only through *Instagram Login*, one account per
sign-in. This adds Meta's *Instagram API with Facebook Login*: when a Facebook
Page is connected on **Messenger Accounts**, the Instagram professional account
attached to that Page is connected too, using the Page's own access token.

Accounts are stored in the existing `instagram_accounts` table (no migration).
The only marker is `token_type = 'page'`; `page_id` holds the Facebook Page id.
They appear on **Link Instagram** and in the inbox like any other.

## New file
| File | Purpose |
|---|---|
| `helper/instaViaFacebook.js` | Finds the Instagram account behind a Page, links it, and picks the right send endpoint. |

## Modified files
- `routes/messenger.js` `/callback`
  - exchanges the login token for a long-lived one (best effort), so Page tokens
    do not expire within hours;
  - after saving the pages, calls `linkInstagramForPages(...)`; the result is shown
    in the popup. Gated by the owner's plan (`instagram_inbox`), exactly like the
    stock Instagram flow. Failures never affect the Messenger connection.
- `helper/socket/function.js` `sendInstaMsg`
  - the POST URL now comes from `messagesUrl(igAccount, API_VERSION)`:
    Page-linked -> `graph.facebook.com/v24.0/<page>/messages` (Page token),
    otherwise unchanged `graph.instagram.com/<ver>/me/messages`.
- `routes/insta.js` webhook `POST`
  - accepts a signature made with **either** `insta_app_secret` or
    `messenger_app_secret`, compared in constant time. Page-linked accounts can be
    signed with the Facebook app secret.

## Meta setup this depends on
1. Login Configuration permissions: add `instagram_basic`,
   `instagram_manage_messages`, `instagram_manage_comments` next to the `pages_*`
   ones. Reconnect afterwards so the new permissions are granted.
2. `instagram` webhook: callback `<BACKURI>/api/insta/webhook/<any>`, same verify
   token, fields `messages` and `comments`.
3. Each Instagram account: Professional, linked to the Page, and "Allow access to
   messages" enabled under Connected tools in Instagram's message settings.

## Tests (`tests/`)
`fake-graph.js` replaces Meta's Graph API so the whole flow runs locally:
`node -r tests/fake-graph.js server.js`, then hit `/api/messenger/callback`.
`send-test.js` checks the send endpoint for Page-linked and legacy accounts.

Verified against the fake: pagination across batches, long-lived token swap,
Instagram linked for the page that has one and skipped for the page that
doesn't, a Graph error on one page not breaking the others, plan gating, send
endpoint per account type (10/10), webhook signature with either secret and
rejection of wrong/tampered/missing signatures (6/6), and an inbound message
landing in the inbox for a Page-linked account.

**Not verified against real Meta.** The fake encodes my reading of Meta's API
(`instagram_business_account` on the Page; `POST /<page>/messages`). If real
responses differ, linking or sending will fail visibly; Instagram-Login accounts
are unaffected.
